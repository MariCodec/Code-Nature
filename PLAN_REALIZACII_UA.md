# План Реалізації Платформи

## Мета

Перетворити поточний застосунок для вивчення HTML/CSS на навчальну платформу з двома основними ролями:

- `учень`
- `викладач`

Платформа має дозволяти:

- учням проходити уроки, виконувати завдання, зберігати код і прогрес
- викладачам переглядати список своїх учнів і відстежувати їхній прогрес

Важливе уточнення:

- поточний MVP залишається `HTML/CSS-first`
- але архітектура не повинна назавжди обмежувати платформу лише HTML/CSS
- у майбутньому мають бути можливі інші напрями, курси, мови програмування і типи уроків

## Поточний Стан Реалізації

На поточний момент частина фронтенд-архітектури вже реалізована.

Що вже зроблено:

- додано нову content-модель
- додано mock `contentApi`
- додано `contentSlice`
- список уроків і сторінка уроку переведені на новий content flow
- реалізовано базовий auth foundation
- маршрути розділені на public / student / teacher
- `userCode` підготовлено до `savedFiles`
- `CodeEditor` почав працювати через lesson files і `savedFiles`
- додано `studentApi` для user-scoped persistence
- `syncThunks` переведено на `studentApi`
- `LessonNavigation` переведено на `contentSlice`
- `LessonPage` частково переведено на прямий `lessonDto`
- `checkLesson` переведено з legacy lesson-shape на DTO-based tasks
- `DocsPage` переведено на новий content flow
- тимчасовий compatibility adapter уже видалено
- code persistence переведено на `savedFiles`-only формат
- progress persistence переведено на DTO-подібний persisted shape

Що це означає:

- ми вже не на етапі "тільки планування"
- фронтенд-міграція вже почалась
- student persistence уже доведено до значно більш backend-ready моделі
- основний legacy-cleanup по content flow уже пройдений
- блок student flow на рівні content + persistence доведений до хорошої проміжної точки
- наступний основний фокус має бути на новому frontend-блоці, а не на продовженні цього migration-cleanup

## Загальний Принцип Реалізації

Правильний порядок робіт:

1. зафіксувати архітектуру MVP
2. реалізувати стабільний `student flow`
3. реалізувати `teacher flow`
4. лише після цього активно наповнювати платформу контентом

Це потрібно, щоб не переробляти пізніше:

- маршрути
- Redux shape
- persistence logic
- auth flow
- сторінки викладача і учня
- модель контенту
- модель курсів і типів уроків

---

## Етап 1. Зафіксувати Архітектуру MVP

### Ціль

Погодити, як саме виглядає продукт на першій версії, і не починати реалізацію без чіткої структури.

### Що треба вирішити

- які є ролі:
  - `student`
  - `teacher`
- яка верхньорівнева модель контенту:
  - `track -> course -> lesson`
- що уроки на MVP вже входять у модель БД
- що саме зберігається в БД
- чи бачить викладач:
  - тільки прогрес
  - чи ще й код учня
- як учень пов’язаний із викладачем:
  - напряму
  - через групи/класи
- яка структура маршрутів
- які типи уроків підтримує система концептуально:
  - `html-css-preview`
  - інші типи в майбутньому

### Що треба описати

- ролі
- сутності
- сторінки
- API-контракти
- що лежить у БД, а що поки лишається у фронтенді

### Результат етапу

Після завершення має бути зрозуміло:

- що саме входить у MVP
- як виглядає модель даних
- як виглядає структура застосунку
- що саме реалізується першим

### Критерій готовності

Є зафіксований документ або набір документів, де визначені:

- ролі
- список сутностей
- список сторінок
- список API endpoint-ів
- рішення щодо уроків: у коді чи в БД

## Етап 2. Спроєктувати Сутності, DTO та API

### Ціль

Зробити так, щоб фронтенд і бекенд працювали через стабільний контракт.

### Мінімальні сутності для MVP

- `Track`
- `Course`
- `Lesson`
- `LessonFile`
- `LessonTheoryBlock`
- `LessonTask`
- `User`
- `TeacherStudent`
- `StudentLessonProgress`
- `StudentTaskProgress`
- `StudentCode`

### Що має бути в БД

- користувачі
- ролі
- треки
- курси
- уроки
- файли уроків
- блоки теорії
- завдання уроків
- зв’язки між викладачами й учнями
- прогрес учнів по уроках
- прогрес учнів по завданнях
- збережені файли учня по уроках

### Що не обов’язково робити в першій реалізації

- адмінку для створення контенту
- окремий UI для редагування уроків
- складну CMS
- групи

Але модель уроку треба вже зараз продумувати як більш загальну:

- урок належить до курсу
- курс належить до напряму або треку
- урок може мати різні типи runtime
- урок може містити один або кілька файлів

### Що треба описати в API

#### Auth

- `POST /auth/register`
- `POST /auth/login`
- `POST /auth/logout`
- `GET /auth/me`

#### Student

- `GET /student/me/progress`
- `GET /student/me/code`
- `GET /student/me/code/:lessonId`
- `PUT /student/me/code/:lessonId`
- `PUT /student/me/progress/:lessonId`

#### Teacher

- `GET /teacher/students`
- `GET /teacher/students/:studentId`
- `GET /teacher/students/:studentId/progress`
- `GET /teacher/students/:studentId/code/:lessonId`

### Що треба підготувати

- DTO для auth
- DTO для progress
- DTO для code
- DTO для списку учнів
- DTO для сторінки конкретного учня
- базову абстракцію для lesson runtime і validation type
- DTO для track/course/lesson content

### Результат етапу

Є зрозуміла основа для реалізації бекенду і фронтенду без розбіжностей у моделях.

### Критерій готовності

Описані:

- структура таблиць
- структура основних DTO
- список endpoint-ів
- очікувані request/response формати

## Етап 3. Реалізувати Auth Foundation

### Ціль

Перейти від мокової авторизації до архітектури, готової до реального бекенду.

### Що треба реалізувати

- реєстрацію
- логін
- завантаження сесії при старті застосунку
- збереження поточного користувача у стані
- збереження ролі користувача
- route guards
- redirect після логіну залежно від ролі

### Що має змінитися у фронтенді

- `AppInitializer` має завантажувати session
- auth state має містити роль
- маршрути мають бути розділені на:
  - public
  - student
  - teacher

### Які сторінки потрібні

- `/login`
- `/register`

### Результат етапу

Застосунок знає:

- хто зараз залогінений
- яка в нього роль
- куди його пускати
- які сторінки йому доступні

### Критерій готовності

- учень не може потрапити на сторінки викладача
- викладач не потрапляє в student area випадково
- після reload session відновлюється

---

## Етап 4. Довести Student Flow До Стабільного Стану

### Ціль

Зробити повністю робочий сценарій для учня.

### Що має вміти учень

- відкрити список уроків
- перейти в урок
- редагувати HTML/CSS
- запускати код
- проходити таски
- зберігати код
- зберігати прогрес
- відновлювати все після перезавантаження

### Що треба реалізувати

- user-scoped persistence
- завантаження курсів і уроків з API
- збереження коду по `userId + lessonId`
- збереження прогресу по `userId`
- завантаження коду з API
- завантаження прогресу з API
- стабільне розблокування уроків і тасків

Навіть якщо в реалізації поки є тільки HTML/CSS, не варто закладати думку, що будь-який урок завжди має лише:

- `html`
- `css`

На рівні абстракції треба передбачити:

- lesson files
- runtime type
- validation type

### Які сторінки потрібні

- `/student`
- `/student/lessons`
- `/student/lessons/:lessonId`
- `/student/progress`

### Що важливо не зламати

- client-side lesson validation
- iframe-based checking
- ordered tasks
- unlock logic

### Результат етапу

Учень може реально користуватись платформою без втрати даних.

### Критерій готовності

- код відновлюється після reload
- прогрес відновлюється після reload
- виконання завдань коректно зберігається
- дані одного учня не змішуються з даними іншого

## Етап 5. Реалізувати Teacher Flow

### Ціль

Дати викладачу мінімально необхідний інструмент для контролю прогресу учнів.

### Що має вміти викладач

- бачити список своїх учнів
- бачити коротку зведену інформацію по кожному
- відкривати сторінку окремого учня
- дивитися прогрес по уроках
- дивитися прогрес по завданнях
- за потреби дивитися код учня

### Які сторінки потрібні

- `/teacher`
- `/teacher/students`
- `/teacher/students/:studentId`

### Що показувати у списку учнів

- ім’я
- email
- скільки уроків завершено
- поточний урок
- остання активність

### Що показувати на сторінці учня

- список уроків
- статус кожного уроку
- виконані/невиконані завдання
- останній збережений код по уроку

### Результат етапу

Викладач бачить навчальний стан учнів, а не просто список акаунтів.

### Критерій готовності

- викладач бачить тільки своїх учнів
- сторінка учня відображає актуальний прогрес
- teacher flow не ламає student flow

## Етап 6. Наповнення Контентом

### Ціль

Після стабілізації логіки почати активно створювати навчальний контент.

### Що входить у цей етап

- створення нових уроків
- написання теорії
- розширення `docs`
- покращення пояснювальних текстів
- візуальні покращення інтерфейсу

### Що робити тут обережно

- не робити масове наповнення до стабільного auth/persistence
- не полірувати UI занадто рано
- не зашивати в архітектуру припущення, що платформа назавжди буде тільки для HTML/CSS
- не намагатися одразу будувати повноцінну CMS для контенту

### Результат етапу

Платформа стає не лише технічно робочою, а й змістовно корисною для навчання.

### Критерій готовності

- є достатня кількість якісних уроків
- docs узгоджені з уроками
- student і teacher flows залишаються стабільними після додавання контенту

---

## Що Робити Прямо Зараз

Найкращий наступний порядок дій:

1. остаточно зафіксувати архітектуру MVP
2. оформити схему сутностей і API
3. додати в модель поняття `track`, `course`, `lesson type`
4. вирішити, чи бачить викладач код учня в MVP
5. перейти до auth foundation
6. після цього реалізувати student persistence

## Що Не Варто Робити Зараз

- не добивати весь UI наперед
- не створювати багато уроків до стабілізації базової архітектури
- не переносити все одразу в БД без чіткої моделі
- не будувати teacher dashboard без готового auth і student persistence
